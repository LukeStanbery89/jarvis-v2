# @lukestanbery/jarvis-server — src architecture

This README explains how the server's source is organized. It is not a usage
guide — see the package `README.md` for prerequisites, endpoints, and
script commands.

## Directory tree

```
src/
├── index.ts       # entry point (composition root: bootstrap + attach WS)
├── app.ts         # Express app factory (GET /health + /api mount + portal static/SPA fallback + /web chat client mount)
├── listener.ts    # transport seam: HTTP(S) server + TLS/redirect listener
├── config.ts      # AppConfig/LlmConfig from environment (session TTL, rate limit, portal/web dirs, TLS…)
├── logger.ts      # shared @lukestanbery/jarvis-logger instance (tag `server`)
├── agent.ts       # runAgent — owns the compiled graph + checkpointer (seam)
├── transport.ts   # toServerFrame — pure AgentEvent → wire-frame mapping
├── ws.ts              # /ws chat endpoint (server ↔ client transport)
├── sessionManager.ts  # createSessionManager — the per-prompt session pipeline (lock→claim→guard→stream→touch→release)
├── modelFileCache.ts  # ModelFileCache + createModelFileHandler — shared download-once model serving (STT + wake)
├── http/
│   ├── middleware.ts       # requireAuth (bearer → cookie fallback) / requireOwner / requireCsrf — fill req.jarv
│   ├── contractValidation.ts # express-openapi-validator mount + spec resolution + error mapping
│   ├── cookies.ts          # parseCookies + jarvis_session cookie name/attributes (__Host- under TLS)
│   ├── authRoutes.ts       # createAuthRouter — the /api management router
│   ├── attachmentRoutes.ts # createAttachmentRouter — POST /api/attachments (#10)
│   ├── cors.ts             # createCorsMiddleware — exact-origin CORS allowlist + preflight (mount BEFORE the contract validator)
│   ├── params.ts           # parseLimit + parseBoolean — query params, in both the coerced and raw form
│   └── rateLimit.ts        # in-memory login/bootstrap throttle
├── attachments/
│   ├── store.ts       # createAttachmentStore — transient image storage (ids, TTL, ownership, magic bytes)
│   └── limiters.ts    # VlCallLimiter + ByteLedger + InFlightLimiter — attachment quotas (NOT RateLimiter)
├── rate/
│   └── fixedWindowQuota.ts # FixedWindowQuota — generic fixed-window call quota (key: user id or guest session/address string)
├── prefs/
│   └── known.ts        # assertKnownPrefs — write validation for the keys a feature reads (unknown keys stay free-form, #143)
├── scheduler/
│   ├── create.ts       # createJobCreator — the one creation/edit/snooze policy for jobs (#90)
│   ├── http.ts         # createJobRouter — /api/jobs CRUD + run history (#90 phase 5)
│   ├── tools.ts        # SCHEDULABLE_TOOLS + resolveSchedulableTool — which tools a scheduled job may call (#90)
│   ├── runner.ts       # createJobRunner — one job's life: claim, execute, record the run, settle, announce (#90)
│   ├── loop.ts         # createScheduler — the tick, the scan bound, and boot recovery (#90)
│   └── time.ts         # resolveWhen — "at 8", "tomorrow at 8", "friday at 8" → one run instant, in the server's local zone (#90)
├── github/
│   ├── client.ts       # createGitHubClient — App JWT → installation token → read a PR, default branch, open a PR (#140)
│   └── comment.ts      # parseCommentRef / quotedReply — a `reply-to` URL → the kind and id GitHub's reply endpoint needs (#140)
├── sandbox/
│   ├── types.ts        # the SandboxRunner seam: specs, handles, listings, crash policy (#141)
│   ├── fake.ts         # createFakeSandbox — in-memory runner with scriptable logs and exits
│   ├── proxy.ts        # the credential broker: derived per-job tokens, job-state checks, model/route allowlist (#141)
│   ├── proxyServer.ts  # the sidecar entrypoint: broker + egress proxy + the server job-state check (#141)
│   ├── egress.ts       # the public-only forward proxy: CONNECT/HTTP, destination-class policy (#141)
│   ├── disk.ts         # workspaceBytes — `du -sk` for the quota watchdog (#141)
│   ├── logs.ts         # createJobLog/sweepCodingLogs — the full run on disk, capped, with retention (#141)
│   ├── logHub.ts       # createCodingLogHub — the in-memory replay/follow window a running job exposes
│   ├── http.ts         # createCodingLogRouter — GET /api/coding-jobs/:id/logs (NDJSON, live or file) (#141)
│   ├── publish.ts      # createGitHubPublisher — push with an installation token; open a PR, or update a follow-up's (#140)
│   ├── ask.ts          # withCodingAsks — relay a parked job's questions into the chat session that asked (#94)
│   └── recovery.ts     # reconcileCodingJobs — the boot matrix: adopt, prune, fail, remove
├── keyedLock.ts        # createKeyedLock — the per-key exclusion set the chat path and the scheduler share
├── notify/
│   ├── types.ts        # NotificationInput/NotifyOutcome + the NotificationChannel seam (capabilities, not assumptions)
│   ├── prefs.ts        # the notify.* pref shapes, shared by the delivery reader (lenient) and the write validator (strict), #143
│   ├── hub.ts          # createNotificationHub — live sockets by user id (who can be pushed to)
│   ├── service.ts      # createNotificationService — record + policy (presence-first, quiet hours, delivery budget)
│   ├── http.ts         # createNotificationRouter — /api/notifications (list/create/read/dismiss/answer)
│   └── channels/
│       └── inApp.ts    # createInAppChannel — the in-app push over /ws (#139 phase 1, the only channel)
├── tts/
│   ├── types.ts        # TtsProvider seam (synthesize + dispose) + TtsSegment
│   ├── kokoro.ts       # Kokoro engine (kokoro-js, lazy dynamic import)
│   ├── segmenter.ts    # tokens → segments (sentence/clause granularity)
│   ├── orchestrator.ts # segments → one sequential synthesis worker → ordered audio
│   └── kokoro-modules.d.ts # ambient types for the optional kokoro-js deps
├── stt/
│   └── model.ts       # SttModelCache — thin STT spec over the shared modelFileCache (#84 P3b, #107 P3)
├── wake/
│   └── model.ts       # WakeModelCache — thin allowlist spec over the shared modelFileCache (#84 P4, #107 P3)
└── llm/
    ├── chatModel.ts   # createChatModel — one of the TWO @langchain/openai import sites (chat path)
    ├── agentGraph.ts  # createAgentGraph + streamAgentTurn (the LangGraph loop)
    ├── toolCallTracker.ts # folds streamed messages into AgentEvents
    ├── visionModel.ts # createVisionModel — the VL analysis call (the other @langchain/openai site)
    ├── event.ts       # AgentEvent union (token/tool/toolResult)
    └── tools/
        ├── index.ts    # tool registry (bound to the model by the graph)
        ├── time.ts     # getCurrentTime tool
        ├── math.ts     # calculate tool (safe arithmetic parser)
        ├── clock.ts    # format12Hour — shared 12-hour clock formatter
        ├── http.ts     # requestJson — the shared provider transport (#103)
        ├── metering.ts # requireSignedInUser + requireMeteredUser + requireMeteredCaller — the shared owner/quota gate (#103, #8, #139)
        ├── analyzeImage.ts # analyzeImage tool (#10)
        ├── getWeather.ts # getWeather tool (#31)
        ├── weather/    # the OpenWeather weather provider (#31)
        ├── webSearch.ts # webSearch tool (#9)
        ├── search/     # the Tavily/Serper search providers (#9)
        ├── homeAssistant.ts # the homeAssistant tool (#15)
        ├── homeAssistant/ # the Home Assistant REST client (#15)
        ├── wikipedia.ts # the wikipedia tool (#8, default-on, guest-admitting)
        ├── wikipedia/  # the MediaWiki Action API client (#8)
        ├── notify.ts   # the sendNotification tool (#139, the first producer)
        ├── jobs.ts     # setTimer / remindMe / scheduleTask / listJobs / cancelJob (#90 phase 3)
        ├── github.ts   # getGitHubIssue / getGitHubPullRequest / listGitHubIssues / createGitHubIssue / commentOnGitHub (#140)
        └── coding.ts   # startCodingJob — the sandboxed coding agent (#141)
```

Accounts, device credentials, and the app database live in the workspace package `@lukestanbery/jarvis-auth`
(see its README): the role-split store (`AppDatabase` = `UserLedger` & `DeviceLedger` & `SessionLedger`, SQLite),
the `CredentialVerifier` seam, the `AuthContext` union (`guest \| authed \| session`), `AuthError`, and the shared
`ownsRow`/`canManage` ownership policy.

## Data flow

```
CLI / WebSocket client
      │  first frame?  {"type":"hello","capabilities":[...]} → stamped for runAgent
      │  first frame?  {"type":"auth","token":...} → authResult (or error + guest)
      │  then          {"prompt": "...", "sessionId": "...", "mode": "text"|"voice"?}
      ▼
ws.ts  handleMessage/watch   (resolve handshake via store; parse + validate prompt via @lukestanbery/jarvis-protocol;
      │                       claim session in ledger with the prompt's mode as its write-once kind, take per-thread lock, arm turn timer)
      │  prompt, sessionId + AuthContext (guest | authed user/device) + capabilities (empty under mode:"voice")
      ▼
agent.ts runAgent            (the brain seam: graph + checkpointer; capabilities conditioned in the system prompt)
      │  AgentEvents: token | tool | toolResult
      ▼
llm/agentGraph.ts streamAgentTurn  (thread seeded from the checkpointer)
      │  messages
      ▼
llm/chatModel.ts createChatModel  (ChatOpenAI → LM Studio /chat/completions)
      │  content deltas + tool calls
      ▼
LM Studio (OpenAI-compatible server)

… and the streamed AgentEvents flow back out, mapped by
transport.ts toServerFrame (pure event → frame) and emitted by
ws.ts sendFrame as chunk / tool / toolResult frames, then {"done": true}.
```

The boundary between the transport and the model stack is `agent.ts`; the
tests mock `runAgent` (`test/ws.test.ts`) so the chat endpoint is exercised
without a live model.

## Key decisions

- **Transport and model never mix.** `ws.ts` only imports `runAgent`; clients
  can be swapped without touching the model layer and vice-versa.
- **Two provider import sites.** `llm/chatModel.ts` (chat) and
  `llm/visionModel.ts` (image analysis) are the only modules that import
  `@langchain/openai`. Swapping backends means changing two factories, not the
  whole pipeline.
- **Conversations are LangGraph threads.** Every `sessionId` maps to a
  persisted thread in the SQLite checkpointer; a fresh thread is primed with
  the system prompt + the user prompt, existing threads just receive the new
  `HumanMessage`. Multi-turn memory therefore survives server restarts.
- **The model loops through tools.** Tool calls are the model's job to
  request and the ToolNode's to run, bounded by `JARVIS_AGENT_MAX_TURNS`. The
  streamed `messages`-mode output is flattened into `AgentEvent`s
  (`token`/`tool`/`toolResult`) by `streamAgentTurn` + the `ToolCallTracker`,
  so transports never see graph internals. The tracker also decides what a
  `token` may open with: whitespace-only filler (the `\n\n` a local model
  emits around its tool calls) is dropped until real text arrives, and every
  tool frame re-opens that rule, because a client starts a new assistant
  bubble after each tool — forwarding the filler drew empty chat bubbles
  ahead of the call.
- **One active response per connection.** A second prompt arriving while a
  response is streaming is rejected with an error frame (see protocol in the
  package README); `active` lives per-connection inside `attachChatServer`. On
  top of that, a **per-thread lock** rejects concurrent turns on the same
  `sessionId` across sockets, and every turn runs under a hard **turn
  timeout** (`options.turnTimeoutMs`, default `DEFAULT_TURN_TIMEOUT_MS`) so the
  lock always drains — the timeout error is emitted by the timer and the
  in-flight generator is `return()`d.
- **Sessions are a ledger, not just threads.** Each prompt claims its
  `sessionId` in the app database (`AppDatabase.claimSession`, atomic
  `INSERT … ON CONFLICT DO NOTHING`) tagging it guest vs owned and
  `text`/`voice`. Guest sockets' claimed sessions are deleted when the socket
  closes (`guestThreads` tracked per connection); owned sessions persist for
  the REST layer to list/delete. `touchSession` keeps `last_active_at` current;
  `threadId` is unique so a session maps one-to-one onto a checkpoint thread.
- **Auth is a first-frame handshake.** A client may authenticate with a device
  token on its first frame (`{ type: "auth", token }` → one `authResult`
  frame); any other first frame, or none, runs the socket as a guest. The
  token is hashed (`SHA-256`) before `AppDatabase.resolveTokenHash` compares it — no
  raw secret is ever logged or persisted. An optional `hello` frame announces
  rendering capabilities and must itself be the very first frame
  (`markdown`/`html`/`image`/`link`/`audio` tokens); `auth` may open the socket or
  immediately follow `hello`. Capabilities are folded into the system prompt
  so the model writes output the client can actually render.
