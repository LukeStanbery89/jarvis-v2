# AGENTS.md

## Stack

- TypeScript (strict, ES2020, CommonJS)
- Monorepo managed with npm workspaces
- Builds via `tsc`
- Tests via Vitest
- Formatting via Prettier (double quotes, 4-space indent)
- Runtime: Node.js 24+

## Architecture

npm workspaces monorepo with independent, publishable packages under `packages/`:

- `packages/protocol` (`@lukestanbery/jarvis-protocol`) — Shared chat wire protocol: the frame types (`chunk`/`tool`/`toolResult`/`done`/`error`), request type, `MAX_SESSION_ID_LENGTH`, and the only parse/serialize implementation. Single source of truth for both sides of the `/ws` socket, zero runtime deps.
- `packages/auth` (`@lukestanbery/jarvis-auth`) — Auth core: the better-sqlite3 app database (`users`/`devices`/`sessions`/`prefs`), account/device/session ledgers, password + device-token crypto, the `CredentialVerifier` seam, the shared row-ownership policy, `AuthError`, and the private-filesystem helpers. Single home for account/credential state, consumed by the server; runtime dep only on better-sqlite3.
- `packages/server` (`@lukestanbery/jarvis-server`) — Express backend server. Exposes `GET /health` (machine health check), a REST management API (`/api`), serves the portal SPA at `/` (when built), and a WebSocket chat endpoint at `/ws` that accepts a prompt and streams back the response generated by a local LLM (LM Studio by default).
- `packages/cli` (`@lukestanbery/jarvis-cli`) — WebSocket chat REPL. Forwards prompts to the server and prints the streamed response. Uses Node's global `WebSocket`; depends only on `@lukestanbery/jarvis-logger` + `@lukestanbery/jarvis-protocol` (no third-party runtime deps).
- `packages/logger` (`@lukestanbery/jarvis-logger`) — Shared leveled logging wrapping Consola. Emits `YYYY-MM-DD HH:mm:ss [LEVEL] tag — message` lines, colored by level; default level `info`, overridable via `JARVIS_LOG_LEVEL`.
- `packages/portal` (`@lukestanbery/jarvis-portal`) — the browser admin portal (issue #24): a private (unpublished) React 19 + Vite 8 SPA served by the server at `/`. Talks only to the server's REST API with cookie sessions + in-memory CSRF nonces. Not CommonJS, not `tsc`-built: Vite `vite build` → static `dist/`; `tsc` is typecheck-only.
- `packages/contracts` (`@lukestanbery/jarvis-contracts`) — Contract-first API specs (issue #35): OpenAPI 3.1 for the REST `/api` surface + `GET /health` (`spec/openapi.yaml`) and AsyncAPI 3.1 for the `/ws` chat channel (`spec/asyncapi.yaml`). Ships generated TS types (openapi-typescript), Redocly bundle/lint, AsyncAPI validation, spec-conformance tests, and the docs tooling (endpoint tables + static HTML reference, `npm run docs:*`). Spec source of truth is the YAML; the `/ws` frame shapes mirror `@lukestanbery/jarvis-protocol` and are kept in sync by conformance tests.

Each package has its own `package.json`, `tsconfig.json` (extends `tsconfig.base.json`), `src/` (or `server` + per-package `test/`), and `README.md`.

Future client types (voice, etc.) should be added as new packages under `packages/`.

## Scripts

Run from the repository root:

| Command                | Description                                                  |
| ---------------------- | ------------------------------------------------------------ |
| `npm install`          | Install all workspace dependencies                           |
| `npm run build`        | Build all packages (`tsc`, plus `vite build` for the portal) |
| `npm run typecheck`    | Type-check all packages (src + tests)                        |
| `npm test`             | Run all package test suites (Vitest)                         |
| `npm run check`        | Build + typecheck + test + format check                      |
| `npm run format`       | Auto-format all files with Prettier                          |
| `npm run format:check` | Verify formatting without modifying files                    |

## Conventions

- Code style is enforced by Prettier (see `.prettierrc.json`): double quotes, 4-space indent.
- Format-on-save is configured for VS Code (`.vscode/settings.json`) and OpenCode (`opencode.json`).
- Every new or modified function/module ships (or updates) a JSDoc `/** ... */` comment describing purpose, callers, and behavior; keep existing doc comments current whenever behavior changes.
- Logging: route all logging through `@lukestanbery/jarvis-logger`, creating one logger per package via `createLogger({ tag })` (see each package's `src/logger.ts`). The logger emits a timestamp, a `[LEVEL]` label, and the tag, so call sites must not prefix messages with `[INFO]`/`[DEBUG]`-style tags. Default level is `info` (DEBUG stays off unless enabled); set `JARVIS_LOG_LEVEL` to `debug`/`warn`/`error` to change it. Never print tracing messages to the client REPL's stdout — the CLI routes diagnostics to stderr so stdout stays reserved for the streamed response.
- Sensitive data: user prompts and streamed response tokens are real user data — log them only through the logger's dedicated methods (`logger.sensitive` / `logger.sensitiveDebug`). Payloads are redacted by default and rendered verbatim only in development (`NODE_ENV=development`, as set by the server's `npm run dev`); never log raw prompts/response payloads in production. `JARVIS_LOG_SENSITIVE` overrides the mode.
- It is acceptable to add `README.md` files to specific subdirectories when their contents are sufficiently complex, unintuitive, or home to non-trivial business logic — such READMEs follow the same keep-current rule.
- Each package is independently publishable to npm (`npm pack --dry-run` from the package to verify contents).
- Do not commit changes unless the user explicitly asks. Never stage, commit, or push without an explicit instruction to do so.

## Rule: keep README files current

Whenever a change makes any `README.md` stale or outdated, update it in the same change. READMEs describe purpose, usage, scripts, and endpoints — keep them accurate, especially when adding/removing scripts, dependencies, endpoints, or package structure.
